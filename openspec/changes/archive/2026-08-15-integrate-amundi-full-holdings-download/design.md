## Context

The ingestion pipeline currently calls `fetch_url()` for every live registry entry. That helper downloads a URL, follows static HTML links, and returns the resulting file. The current Amundi product page is an Angular application: its full-fund holdings control is generated by client-side code rather than exposed as a static anchor. The existing Amundi fixture proves that the expected workbook is XLSX, contains the complete holdings set, and uses fractional weights consumed by `amundi_landing_xlsx_v1`.

The new integration must obtain the same complete holdings through the provider's actual product API without confusing the full `compositionData` collection with the top-ten `breakDowns` data. The browser-generated XLSX remains a compatibility fixture rather than the live transport.

## Goals / Non-Goals

**Goals:**

- Resolve the complete `compositionData` holdings collection for `LU0908500753` through the product API used by its canonical page.
- Reproduce any required Amundi request context, including country, language, or investor profile, from explicit configuration or the canonical source context.
- Validate response shape, completeness, required fields, and weight semantics before normalization.
- Keep fetching strategy separate from `parser_id`.
- Retain `amundi_landing_xlsx_v1` only when the live/recorded workbook remains compatible.
- Fail explicitly on HTML, top-ten-only, empty, malformed, or incomplete holdings results.
- Preserve fixture mode for deterministic tests and offline development.

**Non-Goals:**

- Change the frontend or historical snapshots.
- Support every Amundi product family in the first implementation.
- Infer completeness from a hardcoded row count alone.
- Silently fall back to the top-ten export.

## Decisions

### Separate fetcher strategy from parser strategy

Add an optional registry field such as `fetcher_id`, with `amundi_product_page_v1` selecting the provider-specific resolver. Keep `parser_id` focused on interpreting the downloaded workbook. Entries without a fetcher ID continue using the generic static URL fetcher.

Using the parser ID to select downloading would conflate transport and file interpretation and make future provider fetchers harder to add.

### Reproduce the provider API request rather than automate a browser

The resolver should call `POST /mapi/ProductAPI/getProductsData` directly. The request selects product `LU0908500753`, requests composition fields, and supplies the Swiss professional English context. A browser automation dependency is rejected for production ingestion because the browser only turns the API data into a client-side XLSX.

The resolver may use fixed context for this entry, such as Swiss country, English language, and professional investor profile, but those values should be represented explicitly and tested rather than hidden in a URL string.

### Validate the complete API composition before normalization

The resolver must reject HTML and malformed responses. The validation step must identify `composition.totalNumberOfInstruments` and `composition.compositionData`, confirm their counts agree, confirm required identity/weight fields, and confirm the weight representation matches the attached XLSX fixture's fractional semantics. Only then should rows be normalized using the existing Amundi parser semantics.

Completeness should be represented by structural validation and provider metadata where available, not only a magic minimum row count, because fund composition sizes vary.

### Record the resolved source in provenance

The snapshot should retain the canonical product page as `source_url` and the actual generated/downloaded workbook path or endpoint as `resolved_download_url`, preserving the distinction between identity URL and transport URL.

## Risks / Trade-offs

- [Amundi changes its private API or export request] -> Keep the resolver isolated, use recorded response fixtures, and fail clearly when the contract changes.
- [The full composition is confused with top-ten breakdown data] -> Require `compositionData` and count agreement; reject responses that only contain `breakDowns` or ten rows.
- [Localized context changes column labels or response shape] -> Test the configured CHE/English/professional context and keep parser header aliases broad enough without hiding missing required fields.
- [Live downloads are nondeterministic] -> Keep fixture mode and add captured full-workbook fixtures for parser and resolver tests.
- [Weights switch from fractions to percentages] -> Detect representative values and validate totals before selecting or retaining the parser semantics.

## Migration Plan

1. Capture and reproduce the product API request and response used by the current Amundi page.
2. Add the resolver and optional registry fetcher/context fields.
3. Add recorded workbook and failure fixtures.
4. Validate the workbook and run it through `amundi_landing_xlsx_v1`.
5. Run focused backend tests and one live/manual smoke test.

Rollback removes the Amundi fetcher ID and resolver dispatch, returning the entry to the existing fixture/static-fetch behavior. Historical snapshots remain unchanged.

## Open Questions

The API endpoint and request context are now known: `POST /mapi/ProductAPI/getProductsData`, product `LU0908500753`, Swiss/English/professional context, and composition fields. The implementation should still fail if the response lacks complete composition data.
